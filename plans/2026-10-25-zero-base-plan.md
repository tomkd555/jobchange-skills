## 結論（エグゼクティブサマリー）

本計画では、スキル群を作り直すための**施策 7 件の承認**をお願いします。実施済みの施策はありません。
推奨は施策 A・B・D・E・G の 5 件です。**特に、スキル群の骨格である求人検索を作り直す施策 D と、検索結果を判断材料にする施策 B を強く推奨**します。B は D・E・G と組み合わせて初めて成り立ちます。

実際の転職活動でスキルを使ったのは 2026-09-18 の 1 日だけで、書類も企業研究も完成していません。原因は、成果物を出す前に多くの項目の登録を求める作りにあります。

推奨の 5 件を実施すると、次の効果が見込まれます。
- **最初の成果物までの手数を減らす:** 自己PR や職務経歴書の依頼から提出できる下書きまでを、質問 2 回以内に収めます（2026-09-18 は質問 4 回目で中断）
- **企業研究を応募の判断に使える形にする:** 調査結果を 1 ページにまとめ、応募するかどうかと、面接で何を確かめるかを決める材料にします
- **求人検索をすぐ使えるようにする:** 職歴と転職の軸の登録なしで、3 問に答えるだけで検索を始められます
- **規模を縮める:** スキルを 10 件から 5 件へ、エージェントを 16 件から 3 件へ減らします

### 1.3 明らかになった課題

1. **成果物を出す前に登録を求める作り:**  
   職務経歴書には職歴の登録が、求人検索と適合性評価には職歴と転職の軸の登録が前提です。軸を初めて登録するときだけでも、次の項目に答える必要があります。
   - 転職理由
   - 主な条件
   - 仕事の特性 8 項目

   応募先に合わせた書類は、求人票取込、企業研究、監査、適合性評価の 4 段階を通った後でなければ作れません。原因は、データをそろえてから成果物を作る順序で設計したためです。結果として、利用者は一度もスキル経由で成果物を受け取っていません。

2. **選択式の聞き取りでは実績が集まらない:**  
   聞き取りメモのうち職務の項目は、すべて選択肢から選んだ分類でした（「AWS の設計・構築」「プロジェクトリーダー」など）。数値や具体的な出来事は 1 件も残っていません。一方、2026-09-18 の会話で自己PR に最も役立ったのは、利用者が選択肢を使わずに書いた「社内におけるAWS第一人者　クラウドネイティブなシステムは私が初」でした。原因は、AI が利用者の経歴を推測して選択肢を並べているためです。そのため、回答の手間が大きいわりに、書類に書ける材料が増えません。

3. **自己PR の依頼でスキルが起動しなかった:**  
   書類スキルの起動語には「自己PR」が入っています。しかし 2026-09-18 の会話では、モデルはスキルを起動せずに自分で下書きを書きました。原因として推測できるのは、1.4.0 の書類スキルの説明です。その説明には「hub から振り分けられて動く」とあります。職歴の登録も前提にしています。結果として、創作や誇張を防ぐ監査が働かず、質問も場当たりになりました。

4. **企業研究の成果物が応募の判断に結びつかない:**  
   企業研究のスキルは、次の 8 項目について、出典とエビデンスレベルを付けた記述を JSON に並べます。
   - 理念、事業、財務
   - 報酬、福利厚生、働き方
   - 評判、選考

   一方、求職者が知りたいのは次の 4 点です。
   - 配属先の仕事の実態
   - 残業と年収の実態
   - 直近の業績や報道
   - 面接で確かめるべき点

   現行の成果物は、これらの点に答える組み立てになっていません。また、スキルの文書には、職場の数値を公開している「しょくばらぼ」と「女性の活躍推進企業データベース」を WebFetch では取得できないと書いてあります。口コミサイトはログインが必要です。そのため、調査の根拠は企業サイトと二次情報に限られ、断定を避けた一般論が多くなります。opus のエージェント 2 件と検証スクリプトを通すため、時間もかかります。

5. **求人検索が登録の前提に阻まれ、届く求人の範囲も狭い:**  
   求人検索は、職歴と転職の軸の両方が登録済みでなければ始まりません。そのため、骨格であるはずの求人検索を、利用者は一度も使えていません。また、Indeed は AI のクローラーの名前を挙げて拒否し、Green は GPTBot を拒否しています。スタンバイは、すべてのクローラーに検索と求人のページの取得を禁じています。検索の URL を組み立てて取得できるのは、求人ボックス、マイナビ転職エンジニア、HERP Careers の 3 サイトです。ほかには、`site:` 検索と、企業の採用ページや採用管理サービスのページを使います。結果として、求人の多い大手の転職サイトの検索結果を読めていません。

6. **規模が大きく、実行と保守に手間がかかる:**  
   1 回の実行で、SKILL.md に加えて複数の references を読みます。応募先の書類 1 件で 6 件のエージェントが動きます。実行時間と費用は計測していません。エージェントの数に応じて増えると見込まれます。また、改修を重ねても、実際の活動で試す機会がありませんでした。そのため、効果は確かめていません。

## 2. 提案施策

### 作り直しの方針

施策 A〜G は、次の 5 つの方針に沿っています。手順の中心は、求人検索から求人チェック、書類、面接対策へ進む流れです。

- **成果物を先に出す:** どの依頼にも、最初の応答で下書きか判断材料を返します。
- **事実は書類を作るたびに書き足す:** 利用者の経歴は、書類を作るたびに `career-private/career.md` へ追記します。登録だけを目的にした聞き取りはしません。
- **聞くのは数字と具体例に絞る:** 質問は 1 回 3 問までとし、回答は自由記述で受けます。選択式は、提出先のように答えが決まっている問いに限ります。
- **調査は応募の判断に必要なことに絞る:** 企業研究の結果は、応募の判断と面接の準備に使う 1 ページにまとめます。
- **個人情報の境界と監査の分離は残す:** Web ツールを持つエージェントには、社名と求人票の本文だけを渡します。書類は、作成者と別のコンテキストで 1 回監査します。

### A. 書類スキルを「下書き先行」に作り直す 【要承認・推奨】

`job-change-documents` を、職歴の登録なしで動く形に書き換えます。

- 受け付ける材料は、既存の職務経歴書や履歴書のファイル、または利用者が自由に書いた経歴の箇条書きです。
- 最初の応答で下書きを返します。足りない事実は【 】で示し、推測で埋めません。
- 【 】を埋める質問は 1 回 3 問までにし、数字と具体的な出来事だけを聞きます。
- 扱う書類は次の 5 つです。転職サイトの登録欄に貼る文章も含めます。
  - 自己PR（字数指定つき）
  - 職務経歴書
  - 履歴書
  - 志望動機
  - 英文レジュメ
- 得た事実は `career-private/career.md` に追記し、次の書類で聞き直しません。
- 説明文から「hub から振り分けられて動く」という条件を外し、自己PR や職務経歴書の依頼で直接起動するようにします。
- 完成前に 1 回監査し、`career.md` と照合して創作や誇張を探します。

**メリット:** 依頼から提出できる下書きまでを質問 2 回以内に収められます。聞き取りの結果が、そのまま書類の文になります。  
**デメリット:** `profile.json` のスキーマ検証がなくなるため、経歴の形式を確かめる手段は監査だけになります。  
**検証方法:** 次の 3 つを `career.md` に移したうえで、利用者が自己PR 2000 字を依頼します。
- 既存の聞き取りメモ
- 自己PR の下書き
- 2026-09-18 の会話で得た回答

目標は、質問 2 回以内、10 分以内です。利用者は次の 3 点を確かめます。
- 質問の回数
- 所要時間
- そのまま転職サイトに貼れるか

### B. 「求人チェック」スキルを新設し、求人票取込・企業研究・適合性評価をまとめる 【要承認・推奨】

新しいスキル `job-change-posting-check` を作ります。このスキルは、求人検索で選んだ求人、求人票の URL、貼り付けた本文、画面の画像のどれかを受け取り、1 件ごとに判断材料を返します。結果は `{DATA_ROOT}/companies/{企業スラッグ}/posting-check.md` に、1 件 2,000 字以内で書きます。スカウトのメールを複数まとめて貼った場合は、比較表も付けます。

| 節 | 中身 | 書く担当 |
|---|---|---|
| 条件 | 年収レンジの下限、勤務地、リモート、雇用形態、固定残業代 | 調査担当 |
| 注意点 | 業務や勤務地の変更範囲が無限定、固定残業代の時間が長い、年収レンジの幅が大きい、行政処分や労働基準関係法令違反の公表 | 調査担当 |
| 会社の実態 | 直近の業績、報道、技術ブログや登壇、公的データベースの残業時間と有休取得率 | 調査担当 |
| 希望との照合 | `career-private/wishes.md` の条件ごとに、満たす・満たさない・不明 | メインのセッション |
| 面接で確かめること | 求人票と調査で分からなかった点を、面接での質問にしたもの | メインのセッション |

- 希望条件は、施策 D の求人検索で聞いた `wishes.md` を使います。求人チェックから使い始めた場合も、同じ 3 問を聞きます。
- `wishes.md` と `career.md` は、メインのセッションだけが読みます。調査担当には渡しません。
- 利用者が貼り付けたスカウトのメールからは、メインのセッションが社名と求人の本文だけを抽出して調査担当に渡します。宛名や、利用者の経歴の要約は渡しません。
- 調査の手順には、scan-research の型を取り込みます（施策 G）。
  - 問いを 3〜4 個に分けます。
  - 問いごとに、ツールの呼び出しを 8 回までとします。
  - 悪い評判や処分を探す検索を、必ず 1 回入れます。
  - 数値には、出典ページの引用を付けます。
- エビデンスレベルは公式、報道、口コミの 3 段階とし、本文の文末に添えます。口コミだけを根拠にした記述には、その旨を明記します。
- 企業スラッグの解決には、現行の `company_index.json` と `validate_company_index.py` を引き続き使います。

**メリット:** 1 社あたりのエージェントが 1 件になり、待ち時間と費用が減ると見込まれます。成果物が、応募の判断と面接の準備に直接使えます。  
**デメリット:** 次の 3 つがなくなります。
- 拘束時間と実質時給の計算
- 7 観点での点数評価
- 監査担当による出典の抜き取り確認

**検証方法:** 利用者の手元にある実際の求人 3 件で求人チェックを実行します。1 件ごとに、応募の判断に使えたか、面接の質問に使えたかを利用者が判定します。

### C. 利用者の Chrome 経由の閲覧を調査に加える 【要承認】

WebFetch で取得できないページを、claude-in-chrome で利用者の Chrome から読みます。Chrome を操作するのはメインのセッションで、読んだ数値と出典 URL を調査担当の結果に加えます。対象の範囲を選んでいただく必要があります。

| 範囲 | 読めるようになるもの | リスク |
|---|---|---|
| 公的サイトだけ | しょくばらぼ、女性の活躍推進企業データベースの残業時間、有休取得率、平均勤続年数 | 小さい。検索フォームを通常どおり操作します |
| 転職サイトの検索画面も含める | Indeed、Green、doda の検索結果と求人ページ | robots.txt で AI による取得を拒否しているサイトを、利用者のブラウザで読むことになります。各サイトの利用規約に反するおそれがあります |
| ログイン後の画面も含める | 転職サイトのスカウト本文、口コミサイトの評価と投稿 | 利用者のアカウントで自動的に閲覧するため、各サイトの利用規約に反するおそれがあります |

**メリット:** 職場の数値を公的な出典から取れるようになり、企業研究の根拠が確かになります。転職サイトの検索画面まで含めると、求人検索で読める求人が大きく増えると見込まれます。  
**デメリット:** Chrome と拡張機能を起動しておく必要があります。1 ページごとの操作に時間がかかります。  
**検証方法:** 実在する企業 1 社について、しょくばらぼから月平均の所定外労働時間を取得し、出典 URL 付きで `posting-check.md` に載ることを確かめます。  
**補足:** 推奨は公的サイトだけです。転職サイトの検索画面は、求人検索の効果が最も大きい範囲です。ただし、利用規約の確認は利用者に委ねることになるため、推奨から外しました。ログイン後の画面の内容は、利用者が本文や画像を貼り付ければ読めます。

### D. 求人検索を骨格に据え、登録なしで動く形に作り直す 【要承認・推奨】

`job-change-job-search` を、スキル群の中心として作り直します。

- 職歴と転職の軸の登録を、起動の前提から外します。
- 最初に次の 3 問だけ聞き、答えを `career-private/wishes.md` に保存します。2 回目からは聞きません。
  - 職種や、使いたい技術を表す言葉
  - 年収の下限
  - 勤務地とリモート
- `career.md` があれば、メインのセッションが技術の言葉だけを抽出し、検索語に加えるかを利用者に確かめます。検索担当に渡すのは、匿名化した検索条件だけです。
- 検索先は、現行の 3 系統を残します。
  - URL を組み立てる 3 サイト（求人ボックス、マイナビ転職エンジニア、HERP Careers）
  - `site:` 検索
  - 企業の採用ページと採用管理サービスのページ
- 施策 C で転職サイトの検索画面を対象にした場合は、Indeed、Green、doda の検索結果も加えます。
- 結果は、求人ごとに条件、注意点、希望との照合を 1 行にまとめた一覧で返します。利用者が選んだ求人は、施策 B の求人チェックに進めます。
- 現行の 8 軸の判定と 3 分類は、施策 B と同じ「満たす・満たさない・不明」の照合に揃えます。指示文書は、求人チェックと重なる部分を外して縮めます。

**メリット:** 3 問に答えるだけで、最初の検索結果を受け取れます。検索から応募の判断までが、一続きの手順になります。  
**デメリット:** 現行の 8 軸の判定と、改善軸による基準求人との比較（similar_better）は簡略になります。  
**検証方法:** 作り直す前に、現行の求人検索を利用者の実際の条件で 1 回実行し、件数と、応募を検討したい求人の数を記録します。作り直した後に同じ条件で実行し、両方の数を比べます。

### E. 職歴・転職の軸・自己分析・適合性評価・企業研究の独立スキルを廃止する 【要承認・推奨】

次の 5 件を廃止し、必要な中身を施策 A と B に移します。

| 廃止するスキル | 移す先 |
|---|---|
| `job-change-profile` | 施策 A の `career.md` への追記 |
| `job-change-axis` | 施策 D の `wishes.md`（3 問） |
| `job-change-self-analysis` | 施策 A の自己PR と志望動機（強みと転職理由の言い換え） |
| `job-change-fit-assessment` | 施策 B の「希望との照合」 |
| `job-change-company-research` | 施策 B の「会社の実態」 |

振り分けのスキル `job-change-support` は残し、次のように書き換えます。
- 職歴と転職の軸が登録済みかどうかの確認を外します。
- 振り分け先を、求人検索、求人チェック、書類、面接対策の 4 件にします。
- 設定の確認（`jc_config.py`）と企業スラッグの解決（`validate_company_index.py`）は残します。
- `validate_profile.py`、`validate_axis.py`、`split_profile.py`、`check_freshness.py` とそのテストを削除します。他の 3 スキルの検証スクリプトを読み込む `test_vocabulary_sync.py` も削除します。

残るエージェントは、検索担当、調査担当、書類の監査担当の 3 件です。検索担当と調査担当は Web ツールを持ち、調査担当は面接情報の調査も兼ねます。書類の監査担当は Web ツールを持ちません。書類の作成と模擬面接は、利用者と対話するメインのセッションが行います。

あわせて、`profile.json`、`axis.json`、`self_analysis.json` の JSON 形式と検証スクリプトを廃止します。利用者の情報は、利用者が自分で読み書きできる Markdown に移します。既存の聞き取りメモと自己PR の下書きは、`career.md` へ移します。

**メリット:** 利用者が経歴や希望をエディタで直接書き足せます。検証スクリプトとテストの保守の手間が大きく減ります。  
**デメリット:** 他の利用者が `profile.json` を持っている場合、移行が必要になります。移行には、JSON を読んで `career.md` を書く手順を README に載せて対応します。メジャーバージョンが上がります。  
**検証方法:** 削除後に、残るスキルの単体テストとエージェント定義の一致検査が通ることを確かめます。また、振り分けのスキルから 4 件の振り分け先がそれぞれ起動することを、依頼文 1 件ずつで確かめます。

---

### F. 面接対策と適性検査対策を 1 つのスキルにまとめる 【要承認】

`job-change-interview-prep` に `job-change-exam-prep` の中身を統合します。統合後のスキルは、次の内容を扱います。
- 想定質問と逆質問
- 模擬面接と回答の講評
- 選考で使われる適性検査の種類と対策

あわせて、次の 3 点を書き換えます。
- 読む情報を、`profile.json` と転職の軸から `career.md` と `wishes.md` に替えます。
- 模擬面接と講評は、面接対策担当のエージェントからメインのセッションに移します。
- 面接情報と適性検査の種類の調査は、施策 B の調査担当に移します。

求人チェックの「面接で確かめること」を、逆質問の材料にします。

**メリット:** 選考準備の依頼先が 1 つになります。  
**デメリット:** 適性検査の詳しい対策（問題形式ごとの練習）は簡略になります。  
**検証方法:** 施策 B で調べた 1 社について想定質問と逆質問を作り、利用者が面接の準備に使えるかを判定します。

---

### G. scan-research の調査の型を取り込み、スキルは呼び出さない 【要承認・推奨】

施策 B の調査担当に、scan-research の手順の型を取り込みます。scan-research のスキル自体は呼び出しません。取り込むのは、施策 B に着手する時点の scan-research の版です。research-skill は、本計画の対象に含めません。

**メリット:**
1. Web ツールを持つエージェントに個人情報を渡さないことを、job-change のエージェント定義の中で決めておけます。汎用の調査スキルは、呼び出し側が渡したものをそのまま扱います。
2. job-change を単独でインストールしても動きます。

**デメリット:** scan-research を改良しても、求人チェックには自動で反映されません。scan-research の型を変えたときは、求人チェックにも手作業で反映します。
