## 結論（エグゼクティブサマリー）

本計画は、スキル群を 3 本の柱（求人検索、求人チェック、意思決定の支援）で作り直す**施策 7 件**を定めます。7 件とも 2026-10-25 に承認を受けました。承認の過程で、施策 A は希望の受け取り方を自由な一文に、施策 B は項目を求人情報と企業情報の公式な数値に、施策 C はスイング法と 5 通りの順位に、施策 D は一覧からの選択と履歴付きの `wishes.json` に、施策 E は WebFetch で読めない求人ページを含む形に、それぞれ変わりました。利用者のデータは JSON で持ちます。書類作成と面接対策のスキルは、3 本の柱のスキルを実際の転職活動で使って確かめた後に、別の計画で作り直します。

7 件を実施すると、次の効果が見込まれます。
- **最初の成果物までの手数を減らす:** 利用者が希望を一文で書くだけで求人検索を始められ、職歴と転職の軸を先に登録する必要はありません
- **1 社あたりの待ち時間と費用を減らす（見込み）:** 応募先 1 社ごとに起動するエージェントを、6 件から 1 件に減らします
- **応募と内定の判断に根拠を付ける:** 次の 3 点を手順に組み込みます
  - 求人票の法定記載の点検 [E5, E6, E7]
  - 有価証券報告書の読み方 [E17, E24, E25, E26]
  - 効果量の裏付けがあるカウンセリングの構成要素 [E73, E74]
- **保守の対象を減らす:** スキル 10 件・エージェント 16 件・検証スクリプト 19 本を、スキル 4 件・エージェント 2 件・スクリプト 10 本にします

### 1.3 明らかになった課題

1. **成果物の前に登録を求める作り:** 求人検索と適合性評価は、職歴と転職の軸の登録が済むまで動きません。原因は、データをそろえてから成果物を作る順序で設計したためです。結果として、利用者は一度もスキル経由で成果物を受け取っていません。
2. **意思決定の支援が点数で評価する仕組みになっている:** 適合性評価は 7 観点の点数と総合判定を返します。調査では、重み付けの手法ごとに異なる重みが出ること [E41] と、利用者が単純な手法を好むこと [E54] が分かりました。MAUT や AHP を使って職業選択が良くなったと示す研究は、見つかりませんでした。一方、効果量の裏付けがあるのは次の 5 つの構成要素です [E73, E74]。
   - 意思決定の進め方の説明
   - 思い込みの書き換え（認知的再構成）
   - 選択肢ごとの書き出し
   - 個別のフィードバック
   - 行動を妨げる事情への目配り

   結果として、現行の点数が利用者の判断を助けるという根拠はありません。
3. **自己分析が選択に結びつかない:** 自己分析スキルは、求人が目の前にない段階で強みと価値観を書き出します。調査では、本人が感じる適合の度合いから応募先への魅力は予測できましたが、職業の選択は予測できませんでした。選択を左右したのは職務の特性でした [E121]。何を重視するかは、比べる相手や状況で変わります [E129]。結果として、先に作った自己分析は、求人を比べる場面で使われません。
4. **企業研究の成果物が応募の判断に結びつかない:** 企業研究は 8 項目の記述を JSON に並べます。求職者が知りたいのは、次の 4 点です。
   - 配属先の仕事の実態
   - 残業と年収の実態
   - 直近の業績
   - 面接で確かめる点

   原因は、項目をもれなく並べることを目標に成果物を設計したためです。結果として、応募を判断する材料になっていません。
5. **求人検索が読める範囲を把握していない:** Indeed Japan は robots.txt で、クローラーが求人ページを読むことを禁止しています。AI クローラーには別の規則を設けています。Green は、すべてのクローラーに対して検索結果の URL を読むことを禁止しています [E13, E14, E15]。一方、転職者の 45.1% が求人サイトや求人情報誌を使い、13.5% が企業のホームページを使っています [E10, E11]。結果として、検索スキルは読めるサイトを示さないまま、検索結果の件数を市場の大きさとして示すおそれがあります。1 事業者の推計では、求人の 18%〜22% が採用に至らないゴーストジョブでした [E138]。
6. **規模が大きく、実行と保守に手間がかかる:** 1 回の実行で複数の references を読み、応募先 1 社で 6 件のエージェントが動きます。改修を重ねても実地で試す機会がなかったため、効果は確かめていません。

## 2. 提案施策

### 作り直しの方針

施策 A〜F は、次の 5 つの方針に沿っています。手順の中心は、求人検索から求人チェック、意思決定の支援へ進む流れです。

- **成果物を先に出す:** どの依頼にも、最初の応答で検索結果か判断材料を返します。
- **決めるのは利用者:** スキルは選択肢を書き出し、トレードオフを問い、根拠を示します。順位を確定し、判断するのは利用者です。支援が誤っていると、支援がない場合より判断の誤りが増えるためです [E133, E134]。
- **事実には出典を付ける:** Web 検索に基づく AI の回答を調べた研究では、文の約 30% が引用元に書かれていない内容でした [E135]。すべての事実に出典 URL を添えます。
- **個人情報の境界と監査の分離を残す:** Web ツールを使えるエージェントには、社名と求人票の本文だけを渡します。個人情報保護委員会は、生成 AI への個人情報の入力に注意を促しています [E141, E142]。
- **利用者のデータは JSON で持つ:** 希望の条件、求人ごとの調査結果、意思決定の記録を JSON に書き、複数の求人を同じ基準で読めるようにします。表示はチャットの返答に書きます。

### A. 求人検索を、登録なしで動く入口に作り直す 【承認済み】

`job-change-job-search` を、スキル群の入口として作り直します。

- 職歴と転職の軸の登録を、起動の前提から外します。
- 希望は自由な一文（「リモート中心、年収 600 万円以上、SaaS 業界」）で受け取ります。スキルがそれを現行と同じ 6 項目の条件シート（職種、業界、年収の下限、勤務地とリモート、雇用形態、その他）に整え、あいまいな項目だけを確認します。問いは 0〜2 回です。年収の下限と勤務地とリモートは必須条件として記録します。
- 条件シートは `career-private/wishes.json` に保存し、2 回目からは聞きません。
- 現在の勤務先名と現在の年収は聞かず、記録しません。現行の `--profile` による現在の勤務先の除外と、`--profile` と `--axis` による年収の漏れの検査は、入力がなくなるため削除します。
- 検索先は次の 3 系統です。
  - URL を組み立てて読める求人ボックス、マイナビ転職エンジニア、HERP Careers
  - `site:` 検索
  - 企業の採用ページと採用管理サービスのページ
- Indeed と Green の求人は robots.txt で自動取得を拒否しているため [E13, E14, E15]、検索担当のエージェントは読みません。施策 E により、メインのセッションが利用者の Chrome で開いて読みます。
- 求人 1 件ごとに、法定記載の項目を点検表で確かめます [E5, E6, E7, E36]。欠けている項目は「要確認」と表示します。点検結果は検索結果の `legal_check`、必須条件との照合は `must_match` として `references/job-search-format.md` に定義します。
  - 業務と勤務地の変更の範囲
  - 有期契約の更新基準
  - 掲載日
  - 給与レンジの幅
- 結果は一覧で返します。一覧には求人ごとに 1 行で、条件、注意点、必須条件との照合（満たす・満たさない・不明）を載せます。横には公表された給与レンジを示します [E35]。
- 検索結果の件数を、市場の大きさとして示しません。紹介会社限定の求人の割合は「不明」と表示します。
- 検索担当のエージェント 1 件（Web ツール有）は、匿名化した検索条件だけを受け取ります。現行の `agents/job-change-job-searcher.md` と `references/roles/` の写しを、この条件に合わせて書き直します。

**メリット:** 希望を一文で書くだけで最初の検索結果を受け取れます。利用者が何も入力しなくても、法定記載の点検で求人票に欠けている項目が分かります。  
**デメリット:** 現行の 8 軸の判定と、基準求人を上回る求人の検索（similar_better）は簡略になります。  
**検証方法:** 作り直す前に、現行の検索担当エージェントを利用者の実際の条件で 1 回起動し、件数と、応募を検討したい求人の数を記録します。現行の振り分けは登録のゲートで止まるため、メインのセッションがエージェントを直接起動し、その旨を記録に残します。起動の条件は、モード fuzzy、primary set の 1 レーンだけとし、条件シートはメインのセッションが利用者の希望の一文から書きます。応募を検討したいかどうかは、利用者が結果 1 件ごとに印を付けます。作り直した後に同じ条件と同じ判定の仕方で実行し、両方の数を比べます。合格の線は、応募を検討したい求人の数が、作り直す前と同じか多いことです。

### B. 企業研究と求人票取込を「求人チェック」1 件の JSON にまとめる 【承認済み】

新しいスキル `job-change-posting-check` を作ります。このスキルは、次のどれかを受け取ります。
- 求人検索で選んだ求人
- 求人票の URL
- 貼り付けた本文
- スカウトメール

受け取った求人 1 件ごとに、求人 ID（`{企業スラッグ}-{取得日}-{連番}`）を付け、調査結果を `{DATA_ROOT}/companies/{企業スラッグ}/postings/{求人 ID}/posting-check.json` に書きます。同じ会社の 2 件目の求人やスカウトメールは、別の求人 ID の別ファイルになります。希望条件との照合と未確認の項目は、個人情報を含むため、メインのセッションが `{DATA_ROOT}/career-private/matches/{求人 ID}.json` に書きます。調査担当のエージェント（Web ツール有）は `career-private/` を読みません。表示はチャットの返答に書きます。

| 区分 | 項目 | 出どころ | 書く担当 | 書き先 |
|---|---|---|---|---|
| 求人情報 | 会社名、職種名、雇用形態、勤務地、リモートの方針 | 求人票（現行の `job_posting.json` の項目） | 調査担当 | posting-check.json |
| 求人情報 | 給与（下限、上限、基準）、固定残業代の有無と時間数 | 求人票 [E35, E36] | 調査担当 | posting-check.json |
| 求人情報 | 所定労働時間、年間休日、月平均残業時間、有給休暇の取得率 | 求人票（現行の `metrics`） | 調査担当 | posting-check.json |
| 求人情報 | 業務の変更の範囲、勤務地の変更の範囲、有期契約の更新上限 | 求人票（現行の `scope_of_change`）、職業安定法の明示事項 [E5, E6] | 調査担当 | posting-check.json |

調査は次の手順で進めます。
- 問いを 3〜4 個に分ける
- ツールの呼び出しは問いごとに 8 回までとする
- 労働基準関係法令違反の公表を探す検索を 1 回入れる
- 数値には出典ページの引用を付ける

出典は公式（有価証券報告書、厚生労働省、求人票）に限ります。調査担当のエージェント 1 件（Web ツール有）には、社名と求人の本文だけを渡します。`wishes.json` と `matches/` は、メインのセッションだけが読みます。企業スラッグの解決には、現行の `company_index.json` と `validate_company_index.py` を引き続き使います。`posting-check.json` と `matches/` は、書き直す `pii-boundary.md` の対象ファイルに加えます。

**メリット:** 1 社あたりのエージェントが 1 件になります。成果物が応募の判断に直接使え、意思決定の支援が同じ基準で読めます。
**デメリット:** 次の 3 つがなくなります。拘束時間と実質時給の計算、7 観点の点数評価、監査担当による出典の抜き取り確認です。
**検証方法:** 利用者の手元にある実際の求人 3 件で求人チェックを実行します。1 件ごとに、応募の判断に使えたかを利用者が判定します。合格の線は、3 件中 2 件以上で使えたことです。

### C. 意思決定の支援スキルを新設し、「書き出して比べる」手順にする 【承認済み】

新しいスキル `job-change-decision` を作ります。posting-check.json と matches の JSON を済ませた 2〜5 件の求人や内定を受け取り、利用者が決めるまでの手順を進めます。成果物は `{DATA_ROOT}/career-private/decisions/{日付}-{件名}.json` です。手順は、効果量の裏付けがあるカウンセリングの構成要素（選択肢ごとの書き出し、個別のフィードバック、障害への目配り）[E73, E74] と、Gati と Asher の PIC モデル（事前選別、詳細な探索、選択）[E103] に合わせます。

1. **必須と希望の確認:** `wishes.json` の条件のうち `level` が未設定のものだけを 1 つずつ確認し、`must` か `want` を記録します。施策 A と D で既に設定した条件は確認しません。
2. **必須条件で絞る:** `must` の条件だけで候補を絞り、比べる候補を確定します。値が不明の候補は残し、不明と印を付けます。確定後は候補を加えません。選ばなかった選択肢にこだわると、満足度が下がるためです [E60]。
3. **比べる項目の決め方:** 固定の項目表は持ちません。項目は、`wishes.json` の `active` な条件と、posting-check.json の項目のうち候補の間で値が異なるものから作ります。すべての候補で同じ値の項目と、すべての候補で値が不明の項目は表から外します。一部の候補だけ不明の項目は、そのセルを不明として残し、手順 6 に載せます。
4. **値の換算:** 数値の項目は、候補の中の最悪の値を 0、最良の値を 1 として線形に換算します。小さいほど良い項目（残業時間、通勤時間）は辞書の向きに従って反転します。数値にならない項目は、利用者が候補ごとに 1〜5 で評点し、1 を 0、5 を 1 に換算します。順位は、換算した値に重みを掛けた合計で決めます。
5. **重みの聞き方（スイング法）:** 「すべての項目が候補の中で一番低い値だとして、1 つだけ一番高い値に変えられるならどの項目か」を聞き、残りの項目で繰り返して項目の順位を作ります。問いの数は項目数より 1 つ少ない数です。次に 1 位を 100 として他の項目に 0〜100 の点を付けてもらい、合計が 1 になるように正規化して重みとします。候補の間の値の幅を見ながら答えるため、重要度を 1〜10 で聞く方法より候補の差を反映します [E38, E39]。基準を細かく分けると分けた基準の重みが合わせて大きくなるため、項目は 1 つの階層で聞きます [E40, E48]。前回の記録があれば、同じ `field_id` か `condition_id` の重みを引き継いで今回の項目の中で正規化し直し、新しい項目だけを聞きます。
6. **順位の見せ方:** 次の 5 通りを 1 つの表に並べます。手順 5 の重みによる順位、順位重心法（i 番目の重みは 1/n × Σ(k=i..n) 1/k）による順位 [E52]、等重みの順位、`want` を満たす数による順位、手順 5 の重みを 1 項目ずつ 20% 増減し他の重みを比例配分して合計 1 に戻したときに 1 位が変わるかの確認です。手法によって重みが変わるため、1 通りの順位で決めさせません [E41]。
7. **選びたい候補の確認:** 利用者が選びたいと述べた候補について、希望条件を満たさない項目、候補の中で最下位の項目、未確認の項目の 3 つを表にします。
8. **記録:** `decisions/{日付}-{件名}.json` に、候補（求人 ID と企業スラッグ）、比べた項目と各候補の値、重みと 5 通りの順位、決めた候補、決め手にした項目の ID、妥協した項目の ID、入社後の振り返りの欄（入社 3 か月後と 1 年後の満足度と、妥協した項目の実態。空欄で作る）を書きます。十分な根拠をもって決めた記録は、後の後悔を減らすためです [E91]。

偏りへの注意は、該当する場面でだけ 1 文添えます。対象は次の 3 つです。給与の金額に引きずられるアンカリング [E92]、1 つの条件を実際より重く感じる焦点化の錯覚 [E64]、締め切りに追われる焦りです。

**やらないこと:** AHP や MAUT の計算エンジンを中核にしません。進め方の説明を表示しません。1 回限りの採点セッションにしません。1 時間のワークショップでは効果が見られず、逆効果のおそれも示されたためです [E69]。スキルが結論を出しません。

**メリット:** 比較の表、重み、決めた理由が項目の値として残ります。次の比較では前回の重みを引き継げ、振り返りの欄がたまると、どの項目の妥協が後悔につながったかを見返せます。エージェントを起動せずメインのセッションだけで動くため、個人情報を Web ツールに渡しません。
**デメリット:** 利用者がスイング法の問いと評点に答える手間がかかります。項目が 5 つなら、順位の問いが 4 問、点付けが 1 回、数値にならない項目の評点が候補数分です。
**検証方法:** 施策 B で調べた求人 2 件以上を使って 1 回比較します。合格の線は、手順 5 の問いが項目数以内で済み、決めた候補と理由が記録され、利用者がその記録を内定の判断に使えたと判定することです。

### D. 自己分析と転職の軸のスキルを廃止し、価値観は希望の条件として扱う 【承認済み】

`job-change-self-analysis` と `job-change-axis` を廃止します。価値観は、施策 C の比較の前に次の手順で `wishes.json` の条件として記録し、比較の項目として使います。

7. **比較での使い方:** 施策 C の手順 3 で、`active` な条件が比較表の行になります。候補ごとに、スキルは posting-check.json から判断の目安に当たる記載を並べて示し、利用者が 1〜5 で評点します（施策 C の手順 4）。

**メリット:** 自己分析のための聞き取りがなくなり、選んだ項目と書いた条件がそのまま比較の項目になります。条件の変更の記録が残り、どの比較で使ったかをたどれます。
**デメリット:** 初回は一覧の選択に 3 問、必須か希望かの確認に条件の数だけの問いがかかります。
**検証方法:** 施策 C の検証で、`wishes.json` の `active` な条件が比較表の行として使われ、`history` に変更が記録されることを確かめます。

### E. WebFetch で読めないページを、利用者の Chrome で読む 【承認済み】

WebFetch で取得できないページを、メインのセッションが claude-in-chrome で利用者の Chrome を操作して読みます。対象は次の 2 種類です。

- しょくばらぼ（厚生労働省の職場情報の検索サイト）。検索フォームを操作して初めて企業ごとの数値を表示するため、WebFetch では読めません。読む項目は、月平均の所定外労働時間、有給休暇の取得率、平均勤続年数の 3 つです。
- 求人ページのうち、WebFetch で取得できないもの。Indeed と Green のように robots.txt で自動取得を拒否しているサイト [E13, E14, E15] と、ログインや動的な描画を要するページを含みます。

読んだ数値と本文は、出典 URL を付けて posting-check.json に書きます。しょくばらぼの値は、求人票や有価証券報告書の同じ項目の値とは別に、出どころを付けて並べて持ちます。Chrome を操作するのはメインのセッションで、調査担当のエージェントには Chrome の操作を渡しません。`job-change-job-search` と `job-change-posting-check` の `allowed-tools` に、claude-in-chrome の MCP ツールと ToolSearch を加えます。robots.txt で自動取得を拒否しているサイトを利用者のブラウザで読むことについては、各サイトの利用規約の確認を利用者の判断とします。

**メリット:** 残業時間と有給休暇の取得率を公的な出典から取れ、求人票の数値と突き合わせられます。求人検索と求人チェックが、Indeed と Green の求人ページも読めます。
**デメリット:** Chrome と拡張機能を起動しておく必要があり、1 ページごとに Chrome の操作時間がかかります。
**検証方法:** 実在する企業 1 社について、しょくばらぼから月平均の所定外労働時間を取得し、出典 URL 付きで posting-check.json に載ることを確かめます。Indeed の求人ページ 1 件を Chrome で読み、posting-check.json の求人情報が埋まることを確かめます。

### G. 4 種類の JSON に共通するデータ設計 【承認済み】

施策 A〜F で作る `wishes.json`、`posting-check.json`、`matches/` の JSON、decisions の JSON は、同じ項目 ID と同じ値の形を使います。項目の辞書を 1 か所に持ち、4 つのファイルと検証スクリプトがそれを参照します。

**項目の辞書（`skills/job-change-support/references/field-catalog.md`）:** 比較や照合に使う項目を 1 行ずつ定めます。列は `field_id`、日本語の表示名、型、単位、向き（大きいほど良い・小さいほど良い・向きなし）、出どころ（求人票・有価証券報告書・利用者）です。例は次のとおりです。

| field_id | 表示名 | 型 | 単位 | 向き | 出どころ |
|---|---|---|---|---|---|
| `salary_min` | 年収の下限 | 整数 | 円（年額） | 大きいほど良い | 求人票 |
| `remote_days_per_week` | 週のリモート日数 | 整数 | 日 | 大きいほど良い | 求人票 |
| `monthly_overtime_h` | 月平均残業時間 | 数値 | 時間 | 小さいほど良い | 求人票、しょくばらぼ |
| `annual_holidays` | 年間休日 | 整数 | 日 | 大きいほど良い | 求人票 |
| `avg_tenure_years` | 平均勤続年数 | 数値 | 年 | 大きいほど良い | 有価証券報告書 |
| `operating_margin` | 営業利益率 | 数値 | % | 大きいほど良い | 有価証券報告書 |
| `scope_of_change_duties` | 業務の変更の範囲 | 文字列 | | 向きなし | 求人票 |

※辞書の全項目は施策 B の表の項目と施策 A の条件シートの 6 項目で、30 行前後です。利用者が自分の言葉で書いた価値観の条件は `field_id` を `custom` とし、`how_to_judge` で評点の目安を持ちます。

**値の形:** 測った値は、どのファイルでも同じ 1 つの形で持ちます。`{"value": 25, "unit": "時間", "source_url": "https://...", "grade": "A", "as_of": "2026-03", "quote": "..."}` です。`value` は数値か文字列か `null`（不明）で、文字列に単位を混ぜません。`grade` は出典の等級（A 公式、B 報道、C 口コミ）で、現行の `evidence-grading.md` を引き継ぎます。

**共通の規則:**
- 日付は `YYYY-MM-DD`、基準時点は `YYYY-MM` か `YYYY` で書きます。
- 金額は円の整数（年額）、割合は 0〜100 の数値、時間は時間単位の数値です。
- 列挙の値（雇用形態、リモートの方針、照合の結果）は英語の `snake_case` で持ち、日本語の表示名は辞書に 1 か所で持ちます。現行の方針（検証スクリプトが比べる列挙値を 1 か所の表と同期する）を引き継ぎます。
- ID は安定させます。企業は現行の `company_index.json` のスラッグ、求人は `{スラッグ}-{取得日}-{連番}`、条件は `c001` からの連番、意思決定の記録は `{日付}-{件名}` です。
- 4 つのファイルは `schema_version` を持ち、旧版の読み込みを 1 版前まで受け付けます。

**ファイル間の参照:**
- `matches/{求人 ID}.json` の `match[]` は `wishes.json` の `condition_id` と、`posting-check.json` の求人 ID を参照します。
- decisions の JSON の `candidates[]` は `posting_id` と `company_slug` を、`criteria[]` は `field_id` か `condition_id` を参照します。
- `wishes.json` の `used_in[]` は decisions の JSON の ID を参照します。
- 検証スクリプトは、参照先が存在することと、`field_id` が辞書にあることを確かめます。

**各ファイルの構造:**
- `wishes.json`: `conditions[]`（施策 D の手順 6 の項目に `field_id`、`operator`（`>=`、`<=`、`==`、`in`）、`unit` を加える）、`history[]`、`used_in[]`。
- `posting-check.json`: `posting_id`、`company_slug`、`source_url`、`fetched_at`、`job`（求人情報。`field_id` をキーにした値の形の集まり）、`company`（企業情報。同じ形。同じ `field_id` に複数の出どころがあるときは配列）。
- `matches/{求人 ID}.json`: `posting_id`、`match[]`（`condition_id`、`result`（`meets`、`not_meets`、`unknown`）、`basis_field_id`）、`unknowns[]`（値が `null` の `field_id` の一覧）。個人情報を含むため `career-private/` に入れ、検証スクリプトは 4 種類目として 1 本加えます。
- decisions の JSON: `id`、`date`、`candidates[]`、`criteria[]`（`field_id` か `condition_id`、向き、候補ごとの値、利用者の評点）、`weights`（手法ごとの重み）、`rankings`（手法ごとの順位）、`sensitivity`、`chosen`、`decisive_fields[]`、`compromised_fields[]`、`follow_up[]`（`at`（`3m`、`1y`）、`date`、`satisfaction`、項目ごとの実態）。

**汎用に使うための出力:** スクリプト `export_flat.py` を 1 本作り、4 つのファイルを「1 行 = 1 候補 × 1 項目」の CSV に書き出します。列は `decision_id`、`posting_id`、`company_slug`、`field_id`、`value`、`unit`、`as_of`、`source_url`、`grade` です。表計算ソフトや別のスクリプトで、求人の比較、条件の変遷、入社後の振り返りをそのまま集計できます。

**メリット:** 4 つのファイルを同じ項目 ID でつなげるため、比較、照合、振り返りの集計が 1 つの辞書で済みます。項目の追加は辞書に 1 行足すだけです。
**デメリット:** 辞書と検証スクリプトの同期を保つ手間が残ります。現行と同じく、Markdown の表と検証スクリプトの定数をテストで同期します。
**検証方法:** 施策 A〜C の実地確認で作られた 4 つのファイルを `export_flat.py` で CSV にし、候補 × 項目の行がもれなく出ることと、参照の検証が通ることを確かめます。
