# 職務経歴書テンプレート（編年体式）

## 使い方

- 同業界・同職種で一貫し、成長の過程を示したいときに選ぶ。形式の指定が無い場合の既定でもある（出典 S1）。
- 職務経歴は古い順に並べ、会社ごとに1ブロックとする。
- 分量は、社会人経験7年程度まで A4 1〜2枚、それ以上は2〜3枚（出典 S8）。職務要約は200〜300字・3〜5行（出典 S2・S8）、自己PRは200〜400字（出典 S8）。
- `{profile.…}` は profile.json のフィールド、`{…}` は求人票・企業研究・作成日など profile.json 以外の入力を指す。`<!-- -->` は作成担当への指針であり、成果物には残さない。
- 値の無い項目を行ごと省くか「特になし」と書くかは、節ごとの `<!-- -->` に従う。
- 応募先が様式を指定した場合は、このテンプレートを使わず指定の様式に従う。

## 構成

```markdown
# 職務経歴書
<!-- 必須。表題を先頭に置き、続く2行の作成日と氏名を右寄せにする（出典 S2・S3・S6・S8）（Markdown では位置指定を付けず、Word・PDF へ書き出すときに整える）。氏名は profile.json に無いため利用者に確認する。日付は提出日とし、西暦・和暦は書類全体で統一する。 -->

{作成日}現在
氏名: {氏名}

## 職務要約
<!-- 必須。{profile.summary} を核に、{profile.basic.years_of_experience}・{profile.basic.current_role} と応募職に関係する実績を200〜300字でまとめる。応募職との接点を先に述べる。summary が空なら {profile.career_history[]} から組み立てる。{profile.career_gaps[]} がある場合、その説明はここか自己PRで用いる。節は省かない。 -->

## 職務経歴
<!-- 必須。{profile.career_history[]} を period の開始年月の古い順に並べ、会社ごとに1ブロックとする。並行して在籍した会社も、それぞれ1ブロックとして書く。 -->

### {profile.career_history[].company}（{profile.career_history[].period}）
<!-- 会社名は正式名称で書く。期間は period をそのまま使う。 -->

- 事業内容: {company_research.事業内容}
- 資本金: {company_research.資本金}
- 従業員数: {company_research.従業員数}
<!-- この3行は profile.json に無い。在籍企業について利用者が示した事実か企業研究の claim から埋め、無ければ行ごと省く。売上高・設立年・上場区分は任意で、同じ扱いとする。創作しない。 -->

- 所属部門・役職: {profile.career_history[].role}
<!-- 管理職の経歴では、部下人数を responsibilities の記述の範囲で添える（出典 S6・S14）。「マネジメント経験」という独立の節は設けない。role が空なら行ごと省く。 -->

- 担当業務
  - {profile.career_history[].responsibilities[]}
<!-- responsibilities の各要素を1行ずつ書く。空なら「担当業務」の見出しごと省く。 -->

- 実績
  - {profile.career_history[].achievements[].description}: {profile.career_history[].achievements[].metric}
<!-- metric は一字一句そのまま引く。丸め・水増しをしない。metric が null の実績には数値を付けず、担当範囲・役割・工夫を事実で書く。営業職では年度ごとに売上・目標達成率・社内順位を並べる（出典 S13）。achievements が空なら「実績」の見出しごと省く。 -->

## 活かせる経験・知識・スキル
<!-- 推奨。{profile.skills.technical[]}・{profile.skills.business[]}・{profile.skills.portable[].skill} から、{求人要件} に対応するものだけを選ぶ。対応するものが無ければ節ごと省く。 -->

## 資格・免許
<!-- 必須。{profile.skills.certifications[]} を並べる。取得年月は profile.json に無いため、利用者が示した場合だけ添える。certifications が空なら「特になし」と書く。節は省かない。 -->

## 自己PR
<!-- 必須。{profile.strengths[]} から強みを1つ、多くて3つ選び、結論→証明→貢献の順で200〜400字（出典 S8）。証明には achievements[].metric を引く。詳しい構成は self-pr.md にある。節は省かない。 -->

## 志望動機・転職理由
<!-- 任意。応募先が求めた場合だけ置く。{profile.job_change_axis.reasons[]} と {company_research} の claim を素材に、200〜300字を目安とする。企業研究が無ければ企業固有の内容は書けないため、節ごと省く。詳しい構成は motivation-rirekisho-field.md にある。 -->
```

## 記入例

```markdown
# 職務経歴書

2026年8月28日現在
氏名: {氏名}

## 職務要約

架空工科大学 情報工学部を卒業後、受託開発で業務システムの設計・実装に携わり、その後 EC 事業会社で基幹 API の設計と5名チームのリードを担ってきた。社会人経験は8年である。2021年4月から9月までは、ビジネス英語の語学研修と AWS 認定資格の取得に向けた学習に専念した。直近では決済基盤のマイクロサービス移行を主導し、ピーク時 API 応答時間を平均820msから310msへ短縮（約62%改善）している。技術選定の裁量が大きい環境で、より上流の意思決定に関わりたいと考えている。

## 職務経歴

### 架空システムソリューションズ株式会社（2018-04〜2021-03）

- 所属部門・役職: ソフトウェアエンジニア
- 担当業務
  - 業務システムの受託開発（Java, Oracle）
  - 顧客要件のヒアリングと基本設計
- 実績
  - 在庫管理バッチの処理最適化: 夜間バッチの実行時間を6時間から2.5時間へ短縮

### 架空リテールテック株式会社（2021-10〜2026-06）

- 事業内容: EC プラットフォームの開発・運営 <!-- 企業研究の claim から。profile.json には無い -->
- 所属部門・役職: バックエンドエンジニア / チームリード
- 担当業務
  - EC 基幹 API の設計・実装（Python, AWS）
  - 5名チームのマネジメントと採用面接
  - 決済基盤のマイクロサービス移行の技術リード
- 実績
  - モノリスからマイクロサービスへの段階移行を主導（2022-04〜2024-03）: ピーク時 API 応答時間を平均820msから310msへ短縮（約62%改善）
  - リリースプロセスの CI/CD 整備（2023-01〜2023-12）: デプロイ頻度を週1回から日次へ（約5倍）、障害回復時間を平均4時間から40分へ短縮

### 架空ヘルスケアラボ株式会社（2023-04〜2026-06）

- 所属部門・役職: 業務委託（副業）／バックエンドエンジニア
- 担当業務
  - 予約システムの API 実装（Python, GCP）
- 実績
  - 予約枠の在庫計算をリアルタイム化: 予約確定までの待ち時間を平均12秒から2秒へ短縮

## 活かせる経験・知識・スキル

- バックエンド開発: Python、Java、PostgreSQL
- クラウドと基盤: AWS（ECS, Lambda, RDS）、Terraform、Docker
- 開発の進め方: 要件定義、アジャイル開発（スクラム）
- チーム運営: チームマネジメント、技術面接、課題の構造化と優先順位付け

## 資格・免許

- 応用情報技術者
- AWS Certified Solutions Architect - Associate

## 自己PR

大規模移行を計画から完遂まで主導した実行力が強みです。決済基盤のモノリスからマイクロサービスへの段階移行では、2022年4月から2024年3月まで技術リードを務め、ピーク時 API 応答時間を平均820msから310msへ短縮（約62%改善）しました。あわせてリリース基盤を刷新し、デプロイ頻度を週1回から日次へ（約5倍）、障害回復時間を平均4時間から40分へ短縮しました。5名のチームでは採用面接と育成も担当しました。既存システムの改善を、計測できる指標に置き換えて進めます。この進め方で貢献いたします。
```
