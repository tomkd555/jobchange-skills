# 志望動機書テンプレート（A4 1枚）

## 使い方

- 応募先が志望動機書の提出を求めたときだけ選ぶ。履歴書・職務経歴書の志望動機欄に書く場合は `motivation-rirekisho-field.md` を使う。
- 分量は800〜1,000字とし、用紙の8割を埋める（出典 M12・M13。M18 は800字程度）。
- 頭語・結語（拝啓・敬具）と時候の挨拶を付けない（出典 M12・M13・M14）。宛名も付けない（出典 M12・M13）。添え状と役割が重なるためである。
- 導入・業界・企業・職種・貢献できることの5段は、段落を分けて続けて書く。段の名前を見出しとして成果物に残さない。応募先へ向けた文章であるため敬体で書く。
- `{profile.…}` は profile.json のフィールド、`{…}` は求人票・企業研究など profile.json 以外の入力を指す。`<!-- -->` は作成担当への指針であり、成果物には残さない。
- 書かないこと: 待遇・勤務条件を主な理由にすること、前職への不満、他社にも通じる社風賛美、「学ばせていただく」型の受け身、「頑張ります」だけの意欲（出典 M1・M2・M6・M11・M14）。

## 構成

```markdown
{作成日}
<!-- 必須。提出日を右寄せで置く（Markdown では位置指定を付けず、Word・PDF へ書き出すときに整える）。西暦・和暦は書類全体で統一する。 -->

# 志望動機書
<!-- 必須。表題は日付の次に中央へ置く（出典 M12・M13）（Markdown では位置指定を付けず、Word・PDF へ書き出すときに整える）。 -->

{氏名}
<!-- 必須。氏名を右寄せで置く（Markdown では位置指定を付けず、Word・PDF へ書き出すときに整える）。profile.json に無いため利用者に確認する。宛名は書かない（出典 M12・M13）。 -->

<!-- 以下の5段は段落として続けて書く。段の名前を見出しとして残さない。合計800〜1,000字（出典 M12・M13）。 -->

【導入】約100字
<!-- 必須。応募する意思と、{profile.basic.current_role}・{profile.basic.years_of_experience} による自分の立ち位置を短く述べ、志望の結論を1文で置く。 -->

【業界】約150〜200字
<!-- 必須。{profile.targets.industries} または応募先の属する業界について、自分がその業界で働き続けたい理由を、経験した事実に結び付けて述べる。業界の一般論だけで終えない。{company_research} の claim があれば根拠に用いる。 -->

【企業】約200字
<!-- 必須。その企業を選ぶ理由を、{company_research} の claim（理念・事業・求める人物像・技術の方針）に固有の要素で述べる。競合他社にも当てはまる内容にしない。{profile.job_change_axis.reasons[]} と対応づける。企業研究が無い場合、この段は書けない。汎用の骨子に留め、企業研究の後に書き直す旨を利用者へ伝える。 -->

【職種】約200字
<!-- 必須。{求人要件} と {profile.career_history[]} の重なりを述べる。数値は {profile.career_history[].achievements[].metric} を一字一句そのまま引く。丸め・水増しをしない。規模・範囲・主体を表す言葉は profile.json が裏づける範囲に限る。 -->

【貢献できること】約200字
<!-- 必須。入社後に何から着手し、どの経験をどう活かすかを述べる。{profile.strengths[]} と、そこに対応する achievements[].metric を根拠にする。「頑張ります」だけの意欲で終わらせない。 -->

<!-- 段落ごとの配分は出典に無く、本スキルの整理。合計800〜1,000字は M12・M13。 -->
```

## 記入例

```markdown
2026年8月28日

# 志望動機書

{氏名}

貴社の中途採用に応募いたします。バックエンドエンジニアとして8年間、EC 基幹システムの設計・実装と5名チームのリードに携わってきました。技術選定の裁量が大きい環境で、より上流の意思決定に関わりたいと考え、貴社を志望いたします。

決済を含む SaaS の領域では、扱う取引量が増えるほど、性能と信頼性を後から作り直す難しさが増していきます。前職でも、モノリスのまま拡張を続けた基幹システムが、ピーク時の応答時間の悪化という形で限界を見せました。移行を経験してわかったのは、性能の問題が事業の成長の速度をそのまま左右するということです。この領域で働き続けたいと考える理由は、システムの構造の改善が事業の数字に直結する点にあります。

貴社を志望する理由は、使う言語とクラウド構成を開発チーム自身が決められる体制と、その判断の過程を技術ブログで公開している姿勢にあります。公開された記事からは、性能の課題を計測から入って解いている進め方が読み取れました。私自身も同じ順序で仕事を進めてきたため、入社後の議論にも早い段階から加われると考えています。技術選定の裁量を求める私の転職の軸は、開発チームへ判断を委ねる貴社の体制とそのまま重なります。

募集職種であるシニアバックエンドエンジニアの職務内容のうち、決済基盤の設計と性能改善は、前職で担当した領域とそのまま重なります。架空リテールテック株式会社では、2022年4月から2024年3月まで決済基盤の技術リードを務め、モノリスからマイクロサービスへの段階移行を主導しました。移行を段階に分け、機能ごとに切り出す順序を決めながら進めた結果、ピーク時 API 応答時間を平均820msから310msへ短縮（約62%改善）しています。

入社後は、まず既存システムの性能と障害の状況を計測し、改善の順序を数値で示すところから始めます。前職ではリリースプロセスの CI/CD 整備も担当し、デプロイ頻度を週1回から日次へ（約5倍）、障害回復時間を平均4時間から40分へ短縮しました。改善の効果を計測できる指標に置き換えたうえで、チームの合意を得ながら進めます。この進め方は貴社でもそのまま活かせます。5名チームのマネジメントと採用面接の経験もあり、開発体制の拡大にも貢献いたします。
```
